# Typed JSON conversion

## Intent

Continue the authorized Specs -> ASD-STE100-based executable intermediate -> binary language goal toward agent-usable general programming. File resources now provide actual input/output, but text cannot explicitly become typed computational data or structured output. Add typed JSON conversion for every currently executable value type, retaining the broader objective (maps/nesting, richer functions/values, arbitrary precision and Python ecosystem remain open).

## Contract

- Source parse: `the system parses JSON text data.raw into data.values`.
- Source format: `the system formats data.values as JSON text into output.text`.
- Supported value types: Int, Bool, Text, List<Int>, List<Text>. Parse source is Text; its destination declaration determines value type. Format destination is Text; its source declaration determines value type. Operands are global fields. Application and C interop only, enforced by Core and direct bytecode/STE. Integer functions and compiler pass bodies reject these statements.
- Core `JsonConversion` has exactly `json_kind=parse|format` and `value_type=<type>` attrs, no node type. Exactly one `json_step` executable Action owner with numeric step_index and optional numeric operation_index. Exactly one `json_source` and `json_destination` typed global operand; no attrs on operand edges or other semantic edges. Derived reads/writes participate in secret checks, independent of descriptive access edges.
- Bytecode `JSON_PARSE` and `JSON_FORMAT` each have exactly `key,source,type` operands. STE: `Parse JSON text {source} as type {type} into field {key}.` and `Format {type} field {source} as JSON text into field {key}.` Operands use technical data identifiers.
- Parse grammar is strict JSON for the destination type: ASCII JSON whitespace only around/between tokens; Int forbids plus/leading zeros/fractions/exponents and must fit i64; Bool is true/false; Text is a JSON string with standard escapes and valid UTF-16 surrogate pairs; lists are flat/homogeneous with existing strict list rules. Reject null, objects, nested arrays, wrong element/value types, trailing content, invalid UTF-8 and lone surrogates. Decoding `-0` yields `0`.
- Format Int uses existing integer transport semantics (optional +/- and leading zeros accepted, no whitespace, i64 checked), then canonical decimal. Format Bool accepts exact runtime true/false. Text formatting applies core_model::json_string, including its control-character escaping policy. Lists are fully validated and canonicalized with the existing list JSON policy. Text format/parse must be safe in-place, immutable copies remain unchanged.
- Input operands and output bytes are each bounded to 1,048,576 UTF-8 bytes. Lists have at most 65,536 items; canonical list result must fit the byte limit. Parsing Text charges max(decoded bytes,1) to the existing shared 64MiB text budget; parsing lists charges canonical bytes to the existing shared 64MiB list budget; parsing Int/Bool charges neither. Every FORMAT result charges max(encoded bytes,1) to text budget only. Temporary parsing/encoding storage is bounded and reclaimed. No hidden intermediate allocation charges.
- Error classes: `AIL-JSON-001` source/Core/protocol/type errors; `AIL-RUNTIME-JSON` missing/malformed runtime values, malformed JSON, mismatched types, invalid UTF-8 or numeric overflow; `AIL-RUNTIME-JSON-LIMIT` input/result byte size, item count or applicable shared allocation limit exceeded. Native scratch allocation failures also use JSON-LIMIT; physical host memory exhaustion is not a portable, recoverable VM error guarantee. Limits are checked before grammar for overlong input; grammar/complete input validation before result encoding/size/budget; destination changes only on success. Do not leak operand contents in diagnostics or conversion traces. Successful trace is `parsed JSON <key>` / `formatted JSON <key>`.
- Existing literal/list/text operations retain their diagnostics, budgets and behavior. Reuse proven parsers/serializers; native helper extraction or relocatable helper variants may share machine-code generation without altering legacy contracts.
- Imports namespace fields only; type names remain opaque. All source ordering, branches, loops, calls and saved-Core/source/STE round trips preserve conversions.

## Validation and example

Independent Python oracle for all five types, strict acceptance/malformed cases, canonical bytes (including controls/Unicode/NUL), in-place aliases, exact/over limits, maximum list length, shared text/list budgets and no double charges. Test source/saved-Core/rendered-source/STE/VM/native, malformed Core/protocol/profile, secret accesses and imports. File example reads JSON list<Int>, computes squares with a function and loop, formats and writes the result plus aggregate Int JSON. Verify actual output files against Python, no benchmark input/oracle changes.
